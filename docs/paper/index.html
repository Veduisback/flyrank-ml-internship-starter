DOOR 1 · ML ENGINEERS & TECHNICAL REVIEWERS Purpose: credibility through explicit methodology, validation and limitations.

Abstract

SEO and editorial teams often have more content to review than they can inspect manually, creating a need for transparent ways to prioritize limited review attention.

This study asks whether historical content-performance signals available before February 28, 2026 can be used to rank content items for human SEO/editorial review.

A logistic-regression model using five historical performance features was evaluated with a client-grouped validation split and compared with a transparent staleness-and-search-demand baseline.

On the held-out-client evaluation population, the model achieved 0.7179 ROC-AUC and 0.9642 Average Precision, compared with 0.4309 ROC-AUC and 0.9109 Average Precision for the baseline.

The resulting research-stage queue is intended as a directional review-prioritization tool rather than an automated content decision system or a causal claim about the effect of refreshing content.

1. Introduction & Problem Statement

Content teams can have more pages to inspect than their available SEO and editorial review capacity allows. The practical decision is therefore not simply whether a page is "good" or "bad", but which pages deserve attention first.

Can historical content-performance signals be used to prioritize which content items should receive human SEO/editorial review?

This study uses information available by February 28, 2026 and examines its relationship with a subsequent March 2026 search-impression outcome.

The case-study framing is deliberately narrow: the system supports the ordering of limited human review attention. It does not decide whether content should be rewritten, whether a refresh will increase traffic, or what change should be made.

Historical signals → Model ranking → Human inspection → Contextual review → Recorded decision

3. Methodology

Model

The model is a pipeline consisting of StandardScaler + LogisticRegression. The model produces a score used for ranking.

Baseline

The transparent baseline is:

days_since_update × log(1 + search_volume)

This baseline combines content age with available search demand and provides an interpretable comparison before relying on the learned model.

Validation design

The primary validation split is grouped by client. Training used 13,693 observations across 13 clients; evaluation used 2,616 observations from 4 held-out clients.

Client overlap: 0.
No client appeared in both the training and held-out evaluation groups.

This design is intended to test whether the ranking signal transfers across clients rather than benefiting from seeing observations from the same client during training.

Leakage checks

  • Features are based on February information.
  • The target is based on March information.
  • The target is not included in the feature frame.
  • No future/outcome tokens were used as features.
  • Feature columns were checked for missingness and type consistency.

These checks reduce obvious leakage risks; they do not establish that every possible source of dataset bias or temporal drift has been eliminated.

5. Limitations & Honest Framing

  • This is a research-stage analysis, not a production deployment.
  • The target is March search impressions, not refresh success.
  • Only four clients were held out for the primary evaluation.
  • The five features do not represent every factor affecting search performance.
  • Historical relationships may change as data distributions change.
  • The 0.75 high-signal cutoff is a heuristic, not a validated business threshold.
  • Model scores are not calibrated probabilities.
  • No causal claim is made about refreshing content.
  • Content age alone is insufficient evidence for an automatic refresh.
Human review remains required. The model ranks items for inspection. It does not automatically rewrite, publish, delete, redirect, canonicalize, or otherwise modify content.

What data?

The project uses the FlyRank pseudonymized internship warehouse, release flyrank_pseudonymized_warehouse_release_v20260703. The broader release contains approximately 79 million production search-data rows.

I constructed a decision-time dataset using February 2026 historical performance signals and evaluated their relationship with a March 2026 search-impression outcome.

How I evaluated it

The main model is a standardized logistic regression. I compared it with a transparent baseline based on content age and search demand.

Rather than randomly mixing observations from the same clients, validation held out entire clients.

13 training clients → 4 held-out clients → 0 client overlap

This makes the evaluation closer to the question of whether a historical ranking signal transfers to clients it did not train on.

The engineering judgment

The important design decision was not simply choosing a model. It was defining what the model was allowed to do.

  • The model supplies a ranking signal.
  • The queue includes human-readable reason codes.
  • Reviewers inspect the underlying content and search context.
  • The model does not automatically rewrite or publish content.
  • The 0.75 signal cutoff is treated as a heuristic.
  • Scores are not presented as calibrated probabilities.

This turns the model from an isolated prediction experiment into a documented decision-support workflow.

What I would improve next

  1. Evaluate additional time periods.
  2. Test score calibration before introducing thresholds.
  3. Measure whether acting on the queue actually changes outcomes.
  4. Monitor feature and outcome drift before considering production use.

Which content should you review first?

A large content portfolio creates a simple operational problem: there can be more pages worth inspecting than a team has time to review.

This project asks whether historical search-performance data can help create a better starting order for that review queue.

The goal is not "automate SEO." The goal is "help a person decide where to look first."

What I measured

The analysis uses a pseudonymized FlyRank search-data warehouse release containing approximately 79 million production rows.

The method, in plain English

First, there is a simple baseline: combine how long ago content was updated with the amount of search demand associated with it.

Then a logistic-regression model looks at five historical performance signals:

  • 30-day impressions
  • 30-day clicks
  • 30-day CTR
  • 30-day average position
  • 30-day organic sessions

The model does not tell an editor what to change. It creates an ordering: higher-ranked items get inspected earlier.

Data → Ranking → Human review → Decision

What this does NOT prove

  • A high score does not prove a page needs a refresh.
  • A high score does not prove a specific edit will increase traffic.
  • The model score is not a calibrated probability.
  • Content age is not a causal explanation for performance.
  • The evaluation does not establish production performance.
The useful output is a better starting order for human attention — not an automated SEO decision.

The main takeaway

Historical search-performance signals can provide a useful research signal for prioritizing human review on the evaluated population.

The strongest next step is not to automatically change more pages. It is to test the workflow over additional time periods and eventually measure whether acting on the queue produces a measurable outcome.
